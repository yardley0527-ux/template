# B群／全能 旅程管理 — 完整邏輯文件

> 對應程式碼：`app/controllers/omnipotent_restock_controller.rb`  
> 對應頁面：`app/views/omnipotent_restock/`  
> 路由：`GET /omnipotent_restock`

---

## 一、背景與目標

### 問題

每次直播結束後，需要手動：
1. 整理補貨名單（哪些人快用完了？）
2. 整理常購名單（直播前要邀請哪些老客戶？）
3. 對這些人貼標籤，下次再發送

這些工作高度重複，邏輯散落在不同地方，容易遺漏。

### 解法

建立一個以訂單資料為唯一真相來源的閉環系統：
- 訂單匯入後自動更新
- 不需要手動貼標籤
- 每天開啟頁面就能看到當前最新名單
- 可直接匯出 CSV 做後續動作

## 二、資料來源

| 資料表 | 用途 |
|---|---|
| `shopline_orders` | 所有訂單明細，含 `product_name`、`order_date`、`email` |
| `shopline_customers` | 客戶基本資料，含卡別、IG 帳號 |
| `OmnipotentAnalysisController::OMNI_EVENTS` | 歷史直播場次清單，用來判斷某筆購買是否為直播期間 |

### B群 = 全能

Shopline 訂單裡沒有「B群」這個 SKU，實際的 `product_name` 都是中文縮寫，例如 `全能1`、`全能2`、`全能5`。

SQL 篩選條件：
```sql
product_name LIKE '%全能%'
```

## 三、核心計算：預計回購日

### 舊方法（已廢棄）

```
預計用完日 = 購買日 + 瓶數 × 30 天
```

問題：嚴重高估多瓶購買者的持有天數。買 6 瓶的客戶，系統說 180 天後才提醒，但實際上他們 89 天就回來了（可能是一天多顆、家人共用、或早一點回購）。

### 新方法：實際回購中位數

從 DB 統計 5,082 筆回購記錄，取每個瓶數群組的中位數：

```ruby
REPURCHASE_MEDIANS = {
  1  => 45,   # 1 瓶：中位數 45 天後回購
  2  => 50,   # 2 瓶：中位數 50 天後回購
  3  => 60,   # 3 瓶：中位數 60 天後回購
  4  => 67,
  6  => 89,
  10 => 106,
  12 => 120
}.freeze
```

**與「瓶數 × 30」的差距：**

| 買幾瓶 | 舊方法（天） | 新方法中位數（天） | 差距 |
|--------|------------|-----------------|------|
| 1 瓶 | 30 | 45 | 舊方法太早提醒 15 天 |
| 2 瓶 | 60 | 50 | 舊方法太晚提醒 10 天 |
| 3 瓶 | 90 | 60 | 舊方法太晚提醒 30 天 |
| 6 瓶 | 180 | 89 | 舊方法太晚提醒 91 天！ |
| 10 瓶 | 300 | 106 | 舊方法太晚提醒 194 天！ |

**瓶數提取邏輯：**

```ruby
def extract_bottles(product_name)
  return 1 if product_name.nil?
  m = product_name.match(/全能(\d+)/)
  m ? m[1].to_i : 1  # 找不到數字預設 1 瓶
end
```

**非標準瓶數的內插：**

對於 REPURCHASE_MEDIANS 裡沒有的瓶數（如 5、7、8 瓶），用線性內插求近似值：

```ruby
def expected_days(bottles)
  return REPURCHASE_MEDIANS[bottles] if REPURCHASE_MEDIANS.key?(bottles)
  keys = REPURCHASE_MEDIANS.keys.sort
  lo = keys.select { |k| k < bottles }.last
  hi = keys.select { |k| k > bottles }.first
  return REPURCHASE_MEDIANS[lo || hi] unless lo && hi
  lo_v = REPURCHASE_MEDIANS[lo]; hi_v = REPURCHASE_MEDIANS[hi]
  (lo_v + (hi_v - lo_v).to_f * (bottles - lo) / (hi - lo)).round
end
```

**最終計算：**

```
預計回購日 = 最後購買日 + expected_days(瓶數)
距今天數   = 預計回購日 - 今天
```

`距今天數` 為負數 → 已超過預計回購日，還沒回來 → 逾期未回購。

## 四、客戶追蹤範圍

### 追蹤對象

- **近一年內**（365 天）有購買過全能的所有客戶
- 每位客戶只取**最後一次**購買紀錄（代表目前的持有狀態）
- 不限定直播場次，任何時間購買的都納入追蹤

### 為什麼是近一年

超過一年沒有回購的客戶，很可能已經流失或轉用其他產品。追蹤範圍太廣會讓名單失去焦點。未來可視需要調整這個閾值。

### 不排除任何購買管道

以前的版本只看「上一檔直播買的人」，這樣會漏掉：
- 直播外自行下單的客戶
- 更早場次買的客戶（可能已經到了預計回購日）

## 五、直播購買識別

在每一筆記錄裡，加上 `from_broadcast` 布林旗標：

```ruby
broadcast_ranges = OmnipotentAnalysisController::OMNI_EVENTS.map do |e|
  e[:date].beginning_of_day..(e[:date] + 3).end_of_day
end

from_broadcast = broadcast_ranges.any? { |r| r.cover?(bought_dt) }
```

直播場次定義：場次日當天 ＋ 後 3 天（訂單可能有延遲）。

前台顯示：直播期間購買的會在「上次購買」旁邊顯示橘色「直播」badge。

## 六、名單分類（4 個 Tab）

### 🔴 逾期未回購（days_left ≤ 0）

已超過預計回購日，還沒有新的全能購買記錄。這些人是最需要主動聯繫的。

### 🟠 即將回購（days_left 1–14）

預計兩週內會回來購買，是直播前最好的預熱對象。

### ⚪ 尚早（days_left > 14）

距離預計回購日還有超過兩週，不需要立刻聯繫。

### 🔵 常購名單（獨立邏輯）

全能歷史購買次數 ≥ 2 次（`LOYAL_THRESHOLD = 2`）的所有客戶。  
和上面三個 tab 不同，常購名單**不考慮現在是否逾期**，只要是有回購習慣的客戶，每場直播前都應該邀請。

常購名單排序：卡別等級（黑>金>銀>白>一般）→ 購買次數（多到少）→ 累計消費（多到少）

## 七、逾期名單的維護標準

796 人不是全部都值得追。根據逾期天數和歷史購買次數，分四個優先度：

| 優先度 | 條件 | 說明 |
|--------|------|------|
| 🔥 最優先 | 逾期 1–90 天 ＋ 買過 3 次以上 | 真正有習慣的客戶，只是暫時流失 |
| 🟡 可以試 | 逾期 1–60 天 ＋ 買過 2 次 | 有點興趣，值得一試 |
| ⚪ 低優先 | 只買過 1 次 | 可能只是試用，ROI 低 |
| ✖ 可能放棄 | 逾期 180 天以上 | 很可能已流失 |

**「全能累計」欄顏色對應：**

| 顏色 | 次數 |
|------|------|
| 深藍（粗體） | 6 次以上 |
| 藍 | 3–5 次 |
| 橘 | 2 次 |
| 灰 | 1 次 |

## 八、CSV 匯出

### 補貨名單（逾期 ＋ 即將回購）

欄位：狀態、姓名、卡別、IG、上次購買、瓶數、預計回購日、距今天數

### 常購名單

欄位：姓名、卡別、IG、全能購買次數、全能累計消費(NT$)、上次購買

兩份 CSV 都加 UTF-8 BOM（`\xEF\xBB\xBF`），確保 Excel 開啟不亂碼。

## 九、每日更新機制

這個頁面**不需要排程工作**。所有計算都在 controller 即時從 DB 查詢，每次開啟頁面就是最新資料。

觸發資料更新的唯一動作：**匯入訂單**（`ImportCustomersJob`）。匯入後再開頁面，名單就自動更新。
